sage.py · the retrieval (RAG) path

How SAGE retrieves a reply

A study sheet for the retrieval part of SAGE: the exact code that runs each step, explained line by line, and how it differs from ordinary RAG.

All code below is quoted from sage.py (line numbers as of 4 Nov 2026). The same functions are in the "Shared helpers" cell (section 3) of SAGE_reproduction.ipynb. For the rest of the code, see the SAGE Code Guide.

First: SAGE is not ordinary RAG

Ordinary RAG (Retrieval-Augmented Generation) has two separate systems. A retriever (BM25, or DPR, which compares embeddings) finds some documents, pastes them into the prompt, and an LLM writes the answer. The paper's "GPT-4o (RAG)" and "DPR" baselines in Table 4 work like this.

SAGE uses "generative retrieval" (also called self-retrieval). The same T5 model that writes replies also does the retrieving: it is only allowed to "write out" a reply that already exists in the training set, and its own probabilities decide which one. Then a second model rewrites the chosen reply.

Ordinary RAGSAGE
Who retrievesA separate retriever (BM25, DPR)The generator itself, by constrained decoding
IndexText or embedding vectorsA 4-number code per reply (ResID) from an RQ-VAE
What is retrievedDocuments / factsPast supporter replies, filtered by strategy
RankingSimilarity scoreCode distance, then the model's own beam score, then psychological re-ranking (Eq. 5)
How it is usedPasted into the LLM promptFed into a fusion T5 as [CAND], which rewrites it (Eq. 6)

Step 1 · Turn text into numbers: embed

sage.py line 186 · used for replies, queries, COMET and HEAL

h = model.encoder(**enc).last_hidden_state
m = enc.attention_mask.unsqueeze(-1).float()
out.append(F.normalize((h * m).sum(1) / m.sum(1), dim=-1).float().cpu())
  1. Run the text through the T5 encoder. Every token gets a vector of 768 numbers.
  2. Make a mask that is 1 for real tokens and 0 for padding, so padding is ignored.
  3. Average the token vectors into one vector for the whole text ("mean pooling"), then scale it to length 1 so that a dot product equals cosine similarity.

Step 2 · Build the index: RQVAE and cmd_build_index

sage.py lines 207 and 241 · paper Section 3.2, Eq. 2 · command python sage.py build-index

The core of the residual quantiser:

for book in self.books:                       # 4 codebooks, 512 vectors each
    cost = torch.cdist(r, book) ** 2
    idx = sinkhorn(cost.detach()) if balance else cost.argmin(1)
    e = book[idx]
    codes.append(idx)
    zq = zq + e
    r = r - e.detach()
  1. Repeat 4 times, once per level. Each level has its own "codebook" of 512 learned prototype vectors.
  2. Measure the distance from what is left (r, the residual) to every prototype.
  3. Pick the nearest prototype. During training, sinkhorn spreads choices evenly so no prototype goes unused.
  4. Look up that prototype's vector.
  5. Write down its number. This is one digit of the ResID.
  6. Keep a running sum of the chosen prototypes (used to train the RQ-VAE).
  7. Subtract it. What is left is smaller and goes to the next level, which codes finer detail.

And what cmd_build_index does with it:

R = embed(model, tok, [e["response"] for e in train])     # every training reply
...train the RQ-VAE for 50 epochs...
codes = rq.codes(R.to(DEV)).cpu()                         # shape [N, 4]
torch.save({"rq": ..., "codes": codes, "emb": R, ...}, "ckpt/index/index.pt")

The index stores, for every training reply, its 4-number code and its vector. A reply might get the code (17, 403, 88, 251).

What to check after running it. The command prints codes used per level and unique ResIDs N/M. If only a few codes are used, many replies share a code and retrieval cannot tell them apart.

Step 3 · Encode the query and pick strategies

sage.py, inside SageModel.respond (line 538) · paper Eq. 3

src = "context: " + ctx_text(e)
q = embed(sr, tok, [src])[0]
qcode = self.rq.codes(q.unsqueeze(0).to(DEV))[0].cpu()
sprob = F.softmax(strategy_logprobs(sr, tok, src) / a.tau, 0)
top_s = [STRATEGIES[j] for j in sprob.topk(a.bs_strat).indices.tolist()]
  1. Build the input text from the last 6 utterances.
  2. Turn the conversation into a vector with the same embed.
  3. Give the conversation its own 4-number code with the same RQ-VAE. (The paper never says how the query gets a code; this is our assumption.)
  4. Ask the T5 how likely it is to start its answer with each of the 8 strategies, and turn that into probabilities. tau makes them sharper or flatter.
  5. Keep the 3 most likely strategies (--bs-strat 3).

Step 4 · Find candidates: resid_topk

sage.py line 365 · paper Section 3.2 (Hamming distance) · this is the "retriever"

def resid_topk(qcode, qemb, codes, emb, mask, r, use_resid=True):
    cos = emb @ qemb
    score = -(codes != qcode).sum(1).float() * 10.0 + cos if use_resid else cos
    score[~mask] = -1e9
    return score.topk(min(r, int(mask.sum()))).indices.tolist()
  1. Inputs: the query's code and vector, every stored code and vector, a mask saying which replies are allowed, and how many to return (r = 20).
  2. Cosine similarity between the query and every stored reply (a number between −1 and 1).
  3. Count how many of the 4 code positions differ (the Hamming distance, 0 to 4). Multiply by −10 so that fewer differences is a higher score, and add cosine to break ties. With --no-resid only cosine is used (an ablation).
  4. Replies that are not allowed get a hopeless score.
  5. Return the positions of the 20 best replies.

It is called once per strategy, and the mask limits it to replies that used that strategy:

for s in top_s:
    mask = torch.tensor([x == s for x in self.strat_of])
    ids = resid_topk(qcode, q, self.codes, self.emb, mask, a.r, use_resid=not a.no_resid)

So for "Question" it returns the 20 closest training replies that were questions, and so on.

Step 5 · Let the model choose: Trie and constrained_beam

sage.py lines 453 and 471 · paper Eq. 4 · this is the "self" in self-retrieval

targets = [target_text(s, train[j]["response"]) for j in ids]   # "[STRAT] s [RESP] reply"
seqs = [tok(t, add_special_tokens=True).input_ids for t in targets]
trie = Trie(seqs)
def allowed(_, ids):
    nxt = trie.next(ids.tolist()[1:])
    return nxt or [tok.eos_token_id]
out = model.generate(**enc, num_beams=beams, prefix_allowed_tokens_fn=allowed, ...)
  1. Write each of the 20 candidates in the same format the model was trained to produce.
  2. Turn each into token IDs.
  3. Build a trie: a tree where candidates that start the same way share branches.
  4. allowed is called at every decoding step with the tokens written so far.
  5. It walks the trie and returns only the tokens that continue one of the candidates. Every other token gets probability zero.
  6. If no candidate continues from here, the only allowed token is "end of sentence".
  7. Beam search keeps the 4 best paths (--br 4). Because of the trie, each finished path is exactly one of the 20 candidates, ranked by how likely the model finds it for this conversation.
Why this matters. In ordinary RAG the retriever's similarity score decides. Here the generator ranks the candidates with the same probabilities it would use to write a reply. With --no-constraint the trie is removed and the model writes freely (Table 6 ablation).

3 strategies × 4 beams gives up to 12 candidates, each kept with its strategy probability.

Step 6 · Re-rank: Eq. 5

sage.py, inside respond, plus p_valid (line 508)

pv = p_valid(sr, tok, ctx_text(e), [c[1] for c in cands])
log_s = torch.tensor([math.log(c[2] + 1e-12) for c in cands]) + torch.log(pv + 1e-12) / a.delta
if kn.get("comet") and not a.no_comet:
    log_s += a.alpha * torch.log((cemb @ ce.T).mean(1).clamp_min(1e-6))
if kn.get("heal") and not a.no_heal:
    log_s += a.beta * torch.log((cemb @ he.T).max(1).values.clamp_min(1e-6))
best = int(log_s.argmax())
  1. p_valid asks the T5 "judge: <conversation> response: <candidate>" and reads the probability of "yes". The model learned this in training with real replies (yes) and replies from other dialogues (no). This is σ_valid.
  2. Start each candidate's score with log(strategy probability) + log(P(yes)) / δ. Logs turn the paper's product into a sum, which is numerically safer.
  3. If COMET inferences exist for this example…
  4. …add α × log(average similarity between the candidate and the COMET inferences). This is σ_comet.
  5. If HEAL expert replies exist…
  6. …add β × log(highest similarity to any HEAL reply). This is σ_heal.
  7. The candidate with the highest total wins. Its strategy is s_star and its text is r_star.
In our Colab runs COMET and HEAL are switched off (--knowledge none), so lines 3–6 do nothing and the score is strategy probability × validity only.

Step 7 · Hand the retrieved reply to the generator

sage.py: fusion_inputs (line 350), FusionT5 (line 322) · paper Eq. 6

ctx = f"[STRAT] {s_star} [CAND] {r_star} [CTX] {ctx_text(e)}"
H  = enc(**ctx).last_hidden_state
HC = enc(**comet).last_hidden_state
HH = enc(**heal).last_hidden_state
l1, l2, l3 = F.softmax(self.lam, 0)
return l1 * H + l2 * ca_c(H, HC) + l3 * ca_h(H, HH)
  1. This is where the "augmented" part of RAG happens. The retrieved reply goes into the generator's input after [CAND], together with the chosen strategy and the conversation.
  2. Encode that input.
  3. Encode the COMET text separately.
  4. Encode the HEAL text separately.
  5. Three learned weights that always add up to 1.
  6. Mix them: the context, plus what the context "finds" in COMET and in HEAL through cross-attention. The decoder writes the final reply from this mix.

The generator learned this in cmd_train_fusion: for each training turn it was given a retrieved reply with the right strategy from a different dialogue, and had to produce the real reply. So it learned to adapt a similar past reply to the current conversation, not to copy it. With --retrieval-only this step is skipped and r_star is the answer.

Check yourself

Questions a supervisor is likely to ask. Try to answer before opening each one.

What is a ResID and which code makes it?

A 4-number code for a reply, made by the RQ-VAE in RQVAE.quantise / RQVAE.codes, built for all training replies by cmd_build_index.

Which function is the retriever?

resid_topk. It ranks stored replies by Hamming distance between ResIDs, with cosine similarity to break ties, limited to one strategy at a time.

Why is it called self-retrieval?

Because the generator itself picks among the candidates: constrained_beam forces T5 to write out one of the retrieved replies, and its own beam scores rank them. There is no separate ranking model.

How is SAGE different from GPT-4o + RAG?

GPT-4o + RAG uses a separate retriever and pastes results into a prompt. SAGE uses learned discrete codes for the index, the generator ranks candidates by constrained decoding, candidates are filtered by support strategy, a psychological re-ranker picks one, and a fusion model rewrites it with COMET and HEAL knowledge.

What happens if no candidate is found?

The code falls back to an "Information" reply (Section 3.3), in respond: if not cands: ....

How would you test whether ResIDs actually help?

Run python sage.py infer --no-resid, which retrieves by cosine only, and compare the scores with the normal run (Table 6 ablation).
